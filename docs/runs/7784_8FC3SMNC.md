Run ends here UNRESOLVED (not a loss, not a win) - blocked entirely by process/bridge failure, not by gameplay.

Post-mortem: binding constraint was an infrastructure crash, not money/scaling/boss/luck/misplay. The only
gameplay decision made (discard toward the diamond flush on Small Blind) was correct and matched the playbook
and `advise` exactly, scoring exactly the estimated 312 vs need 300.

Bridge issues (exact text/behavior):
1. At run start (before any blind was selected), `blind` (SELECT_BLIND) failed 3+ times with exact text
   "ACTION FAILED: blind_on_deck not set yet, retry None" for 90+ seconds of polling even though `s`/`raw`
   showed phase=BLIND_SELECT and blind choices/tags fully populated (`blind_select.on_deck` was JSON `null`).
   Root cause (found in the game's Lovely-dumped source, functions/UI_definitions.lua ~line 1668): the field
   `G.GAME.blind_on_deck` is only set to `'Small'` inside `create_UIBox_blind_select()`, i.e. only once the
   blind-select UI box is actually constructed - this did not happen on the first `start Black Deck` call
   issued from a prior run's GAME_OVER state (run JLH3JSVQ, abandoned before any blind played). Re-issuing
   `start Black Deck` a second time fixed it immediately but silently discarded run JLH3JSVQ and began a brand
   new run (new run_id 8FC3SMNC, new seed/tags/boss). This makes `start` non-idempotent in a way that can
   silently reroll your run if you retry it as a fix.
2. `cash` (CASH_OUT) after a won Small Blind failed 3x with "ACTION FAILED: Round eval blocking events still
   pending, retry shortly None" (each ~2-3s apart), then on the next attempt the bridge process/HTTP server
   became completely unreachable (connection refused) and stayed down through 30+ poll attempts over ~5
   minutes. This is a hard game/bridge crash, not a transient retry-able condition - no amount of `sleep` +
   retry recovered it.

Playbook suggestions:
1. Add to section 0/1: if `start Black Deck` leaves `blind_on_deck` null (SELECT_BLIND keeps failing
   "blind_on_deck not set yet") for more than ~20s of retries, re-issuing `start Black Deck` a second time
   resolves it, BUT it silently starts an entirely new run (new run_id, new seed) - rename/recreate your run
   log to the new run_id immediately and note the discarded one.
2. Add a hard distinction between "ACTION FAILED ... retry" (transient, keep polling) and a bridge that goes
   fully unreachable (connection refused): the latter is a crash, not a retry condition. Since agents are
   told "never restart/kill processes" for this harness, document that a full connection-refused crash during
   ROUND_EVAL/cash-out is currently UNRECOVERABLE by the agent and must be escalated/reported, not endlessly
   retried.
3. `cash` (CASH_OUT) right after a winning hand may need a longer settle time than the standard 2s retry
   window - the 3 observed "blocking events still pending" retries all happened within ~10s before the crash,
   so it's unclear whether the crash was caused by the cash-out timing itself or was coincidental; flag for
   investigation if it recurs on other ports.
